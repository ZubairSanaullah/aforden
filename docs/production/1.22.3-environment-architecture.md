## 1. Executive Summary & Architecture Principles

This document establishes the official environment architecture for the Aforden platform across all execution contexts. The architecture adheres to four core security and operational tenets:

1. **Strict Environment Tier Separation**: No test, branch, or preview deployment ever connects to or mutates production databases, production payment gateways, or live customer communication channels.
2. **Deterministic Client/Server Boundary**: The browser bundle has zero visibility into server-side credentials. Only explicit, non-sensitive configuration keys prefixed with `NEXT_PUBLIC_` are bundled for client evaluation.
3. **Fail-Fast Startup Validation**: Required environment variables and provider configurations are validated at boot via [`lib/config/envValidation.ts`](file:///d:/Download/aforden/lib/config/envValidation.ts) and Next.js [`instrumentation.ts`](file:///d:/Download/aforden/instrumentation.ts). Misconfigured environments fail immediately with actionable diagnostics rather than throwing deep inside user request paths.
4. **Single Source of Truth**: All environment variable definitions, sensitivities, scoping boundaries, and fallback behaviors are reconciled and documented in this specification.

## 2. Environment Tiers Specification

Aforden defines three formal runtime tiers: **Development**, **Preview**, and **Production**.

| Tier | Hosting Plane | Base URL Strategy | Database Target | External Service Integrations Mode | Secret Storage Strategy |
| :--- | :--- | :--- | :--- | :--- | :--- |
| **Development** | Local developer workstation (`npm run dev`) | `http://localhost:3000` | Local PostgreSQL or isolated Dev Supabase instance | **100% Mock / Sandbox**: Paddle sandbox, Brevo sandbox, local/test S3 bucket, Twilio test credentials, Intuit sandbox, GCP sandbox | Local `.env` (strictly `.gitignore`d, never committed) |
| **Preview** | Vercel Serverless (PR & branch builds) | Dynamic: `https://${VERCEL_URL}` | Dedicated Staging Supabase / RDS PostgreSQL (never shared with Production) | **100% Sandbox**: Paddle sandbox with preview webhooks, staging Brevo/Resend domain, staging S3 bucket, sandbox OAuth | Vercel Project Settings scoped strictly to **Preview** |
| **Production** | Vercel Serverless (`main` branch release) | Canonical: `https://aforden.aformix.com` | Clustered Production PostgreSQL (Supabase / RDS with PgBouncer connection pooler) | **100% Live**: Live Paddle API & signing secrets, verified Brevo/Resend DNS domain, production S3 bucket, verified 10DLC Twilio, verified production Intuit/Google apps | Vercel Project Settings scoped strictly to **Production** |

## 5. Client/Server Variable Boundary & Enforcement

### 5.1 The `NEXT_PUBLIC_` Boundary Rule
Next.js App Router strictly isolates server-side environment variables from client-side bundles. By default, only environment variables prefixed with `NEXT_PUBLIC_` are inlined into client JavaScript bundles at compile time.

* **Audited Public Variable Surface**: Only `NEXT_PUBLIC_APP_URL` is defined in client scope.
* **Zero Client Component Secret Access**: No client component (`"use client"`) references server secrets.

### 5.2 Automated CI Boundary Verification Script
To prevent accidental secret leaks into browser bundles, Aforden implements an automated boundary scanner: [`scripts/check-client-env-boundary.ts`](file:///d:/Download/aforden/scripts/check-client-env-boundary.ts).

The script scans all `.ts`, `.tsx`, `.js`, and `.jsx` files under `app/`, `components/`, and `lib/`:
1. Identifies files declaring `"use client"` or `'use client'`.
2. Detects any AST / regex pattern of `process.env.<VAR>` or `process.env["<VAR>"]`.
3. Asserts that every detected variable starts with `NEXT_PUBLIC_`.
4. Immediately fails CI (exit code 1) if any secret pattern (`*_SECRET`, `*_KEY`, `*_TOKEN`, `*_PASSWORD`, `DATABASE_URL`, `*_CREDENTIAL`) is accessed in client-side code.

Boundary integrity is continuously verified in the automated test suite via [`tests/env/client-env-boundary.test.ts`](file:///d:/Download/aforden/tests/env/client-env-boundary.test.ts).

## 6. Startup / Boot-Time Environment Validation

### 6.1 Validation Architecture
Environment variables are validated at server startup via [`lib/config/envValidation.ts`](file:///d:/Download/aforden/lib/config/envValidation.ts) using Zod schema parsing.

```
+-------------------------------------------------------------+
|                      Server Boot Process                    |
| Next.js instrumentation.ts -> register() [runtime: nodejs]  |
+-------------------------------------------------------------+
                              |
                              v
+-------------------------------------------------------------+
|              lib/config/envValidation.ts                    |
| - DATABASE_URL (non-empty, postgresql:// protocol)         |
| - AUTH_SECRET (non-empty string)                            |
| - BILLING_PROVIDER ("PADDLE" | "STRIPE" | "MOCK")           |
| - EMAIL_PROVIDER ("BREVO" | "RESEND")                       |
| - CRON_SECRET (non-empty bearer secret)                     |
| - Provider-specific keys based on active selection:         |
|     * PADDLE: PADDLE_API_KEY, PADDLE_WEBHOOK_SECRET, env   |
|     * STRIPE: STRIPE_SECRET_KEY, STRIPE_WEBHOOK_SECRET     |
|     * BREVO: BREVO_API_KEY, EMAIL_FROM                     |
|     * RESEND: RESEND_API_KEY, EMAIL_FROM                   |
+-------------------------------------------------------------+
                              |
             +----------------+----------------+
             |                                 |
         [Valid]                          [Invalid]
             |                                 |
             v                                 v
+-------------------------+     +-------------------------------+
| Server Ready to Receive |     | Production Runtime:           |
| Incoming HTTP Requests  |     |   Throws                      |
+-------------------------+     |   EnvironmentValidationError  |
                                |   (Process halts with errors) |
                                | Build / Development:          |
                                |   Logs formatted warnings     |
                                +-------------------------------+
```

### 6.2 Next.js Server Hook Integration
Aforden integrates startup validation via Next.js standard [`instrumentation.ts`](file:///d:/Download/aforden/instrumentation.ts):
- Runs **once** when a Node.js serverless container spins up.
- Enforces strict fail-fast semantics in production runtime (`NODE_ENV=production` and `NEXT_PHASE !== 'phase-production-build'`).
- Permits build-time static evaluation (`npm run build`) without crashing if live production API secrets are omitted from the build environment.

## 7. Environment Provisioning Runbook

### 7.1 Provisioning a New Developer Workstation
1. Clone the repository: `git clone git@github.com:ZubairSanaullah/aforden.git`.
2. Install pinned dependencies: `npm install`.
3. Create local environment configuration: `cp .env.example .env`.
4. Configure local database credentials in `.env`:
   ```bash
   DATABASE_URL="postgresql://postgres:postgres@localhost:5432/aforden_dev"
   DIRECT_URL="postgresql://postgres:postgres@localhost:5432/aforden_dev"
   AUTH_SECRET="dev-auth-secret-min-32-chars-0123456789"
   CRON_SECRET="dev-cron-bearer-token"
   ```
5. Run Prisma migrations: `npx prisma migrate dev`.
6. Verify environment boundary and validation:
   ```bash
   npx vitest run tests/env/
   npx tsx scripts/check-client-env-boundary.ts
   ```

### 7.2 Provisioning a Dedicated Staging / Preview Environment
1. In the Vercel Dashboard, navigate to **Settings** $\rightarrow$ **Environment Variables**.
2. Select the **Preview** environment scope.
3. Add all 33 variables from the Source of Truth table using **staging/sandbox credentials**:
   - Set `DATABASE_URL` and `DIRECT_URL` pointing to the dedicated staging database.
   - Set `PADDLE_ENVIRONMENT="sandbox"` with staging Paddle API keys.
   - Set `EMAIL_FROM="staging@aforden.com"`.
   - Set `AWS_S3_BUCKET="aforden-storage-staging"`.
4. Open a Pull Request on GitHub. Verify the automated Preview deployment succeeds and the Vercel bot comments with the preview URL.

### 7.3 Production Environment Secret Rotation
When rotating production secrets (e.g. `CRON_SECRET`, `AUTH_SECRET`, or `PADDLE_API_KEY`):
1. Update the secret value in Vercel Project Settings (**Production** scope).
2. For webhook signing secrets (`PADDLE_WEBHOOK_SECRET`), configure the new secret in the external provider dashboard in dual-signature or grace-period mode if supported.
3. Trigger a production redeployment in Vercel to recycle all running serverless lambdas.
4. Verify `/api/health` returns HTTP 200 `{ "status": "healthy" }`:
   ```bash
   curl -i https://aforden.aformix.com/api/health
   ```
5. Invoke a test cron request:
   ```bash
   curl -i -H "Authorization: Bearer <NEW_CRON_SECRET>" https://aforden.aformix.com/api/cron/session-cleanup
   ```
   Confirm HTTP 200 response.
