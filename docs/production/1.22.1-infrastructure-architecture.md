## 1. Executive Summary

This document establishes the formal production infrastructure architecture for the **Aforden** platform. It audits the runtime surface of the application as built and tested through Phase 1.21.10, classifies external service dependencies into hard and soft boundaries, documents divergence points between development and production environments, and enumerates the open infrastructure decisions requiring user sign-off prior to deployment.

### 2.8 Background Processing, Workers & Scheduled Tasks
Inspection reveals that **zero in-process `setInterval` timers, cron daemons, or queue workers run automatically within the Next.js process**. Instead, the codebase implements stateless batch execution functions designed to be triggered externally:
1. **Notification Outbox Worker**: `processOutboxBatch(prisma, options)` ([`lib/services/notification/outboxProcessorService.ts`](file:///d:/Download/aforden/lib/services/notification/outboxProcessorService.ts)).
2. **Notification Stuck-PROCESSING Scanner**: `reconcileStuckDeliveries` / `reconcileStuckOutbox` ([`lib/services/notification/reconciliationWorker.ts`](file:///d:/Download/aforden/lib/services/notification/reconciliationWorker.ts)).
3. **Billing Dunning Sweep**: `runDunningSweep(prisma, options)` ([`lib/services/billing/dunningService.ts`](file:///d:/Download/aforden/lib/services/billing/dunningService.ts)).
4. **Billing Subscription Reconciliation**: `runReconciliationSweep(prisma, options)` ([`lib/services/billing/reconciliationService.ts`](file:///d:/Download/aforden/lib/services/billing/reconciliationService.ts)).
5. **Automation Polling Worker**: `pollAndProcessDueScheduleJobs(prisma, options)` ([`lib/services/automation/scheduleJobService.ts`](file:///d:/Download/aforden/lib/services/automation/scheduleJobService.ts)).
6. **Integration Retry Orchestrator**: `executeCapabilityWithRetry` ([`lib/integrations/execution/retryOrchestrator.ts`](file:///d:/Download/aforden/lib/integrations/execution/retryOrchestrator.ts)).

*Architectural Consequence*: Production infrastructure **must provide a scheduling trigger** (e.g. Vercel Cron, AWS EventBridge, or an external worker runner) to invoke these routines on an automated schedule.

## 5. Background Task Scheduling Options for Production

Because Next.js serverless functions terminate immediately after serving an HTTP response, long-lived in-process background loops cannot run reliably. Two architectural options exist for running the 6 required background sweeps:

### Option A: Serverless HTTP Sweep Endpoints + Vercel Cron (Recommended for Vercel)
- Create secured administrative route handlers under `app/api/cron/...`:
  - `POST /api/cron/outbox`: Invokes `processOutboxBatch` and `reconcileStuckDeliveries` (every 1 minute).
  - `POST /api/cron/automations`: Invokes `pollAndProcessDueScheduleJobs` (every 1 minute).
  - `POST /api/cron/dunning`: Invokes `runDunningSweep` (every 6 hours).
  - `POST /api/cron/reconciliation`: Invokes `runReconciliationSweep` (every 24 hours).
- Protect all cron routes with a high-entropy bearer secret (`CRON_SECRET`) verified in headers.
- Configure `vercel.json` crons to invoke these routes on their respective schedules.

### Option B: Dedicated Lightweight Worker Process (Recommended for Container/VM)
- Deploy a standalone Node.js container (e.g. on AWS ECS or Railway) running `scripts/worker.ts` that executes an event loop calling the existing service functions at configured intervals.

## 6. Open Judgment Calls Requiring Sign-Off

The following decisions must be explicitly resolved before infrastructure provisioning and deployment (Phase 1.22.2+) can begin:

1. **Target Hosting Platform**:
   - *Option 1 (Recommended)*: **Vercel**. Matches Next.js 16 App Router architecture, provides automated preview deployments, edge middleware, and built-in Vercel Cron for background sweeps.
   - *Option 2*: Container platform (AWS ECS / Railway / Render). Offers persistent worker loops and predictable container networking at the cost of higher maintenance overhead.
   - **Decision Needed**: Confirm whether Vercel is the approved production hosting target.

2. **Database Strategy (Supabase Promotion vs Dedicated Production Project)**:
   - *Option 1 (Recommended)*: Provision a **brand-new, dedicated production Supabase project** in the target production AWS region, keeping the existing Supabase project strictly for development/staging testing.
   - *Option 2*: Promote the existing Supabase project to production after executing a full clean wipe and running the 39 migrations from scratch.
   - **Decision Needed**: Confirm whether to provision a separate production database project.

3. **Distributed Redis Rate Limiting (Closing Residual Risk RR-01)**:
   - *Option 1*: Provision **Upstash Redis** (serverless Redis) or AWS ElastiCache in Phase 1.22.2, install `@upstash/redis` or `ioredis`, and replace `MemoryRateLimitStore` with a distributed sliding-window store to formally close RR-01.
   - *Option 2*: Defer Redis provisioning; deploy the initial production release with single-region edge rate limiting (`MemoryRateLimitStore`) and accept partitioned limits across serverless instances as a known operational boundary.
   - **Decision Needed**: Confirm whether Redis is required for initial production launch.

4. **Production Domain & URL Strategy**:
   - Define the canonical production domain (e.g. `app.aforden.com` or custom domain) so that `AUTH_URL`, `NEXT_PUBLIC_APP_URL`, and Stripe webhook callback URLs can be accurately mapped.
   - **Decision Needed**: Provide the designated production domain name.

5. **Stripe & Resend Production Account Readiness**:
   - Confirm whether production-tier credentials for Stripe (`sk_live_...`) and Resend (with verified DNS SPF/DKIM records for `EMAIL_FROM_ADDRESS`) are ready to be configured, or if initial staging deployments should use test credentials.
   - **Decision Needed**: Confirm credential availability for production staging.
